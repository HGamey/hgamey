# 接续共享研究

研究目标、方向、证据和人类反馈放在节点；推理、优先级和执行回合由外部 Agent 负责。网页 `/dash/research`、`/dash/jobs`、`/dash/results` 与 CLI/API 使用同一份状态。人无需同步在线。

## 取得足够上下文

复用用户已给的目标与授权、现有节点和研究，不重复 onboarding。需要明确节点 URL/持久 node ID、凭据文件路径或环境变量名、research ID、可执行范围，以及运行器已有的时间/行动边界。缺少的信息只阻断依赖它的工作。凭据值不写入研究、脚本正文、日志或交接。

用本仓库 `node/pf-node` 的 `node` 核目标及公布能力；研究需 `research.state-v1`，结果需 `results.index-v1`，提交需幂等任务能力。producer 必须在 `execution.bins`，具体子命令和执行策略也须可用。已部署版本可能落后于本地源码。远程设备操作另见 [hgamey-remote](../hgamey-remote/SKILL.md)；本机 PF 操作沿 phonefarm skill。GOL 是可选方法。

读取当前研究、方向、请求、反馈和已知未决操作/任务；列表沿原过滤条件翻完分页，事件游标按客户端分别保存。事件只含对象身份/版本，不含反馈正文、任务终态、结果登记或设备重连。处理前读所指对象；只有处理并保存相应决定后，才能把本批 `next_cursor` 作为自己的 checkpoint，不能使用全流 `head` 代替。阅读期间发生的更新可补读事件，采取动作前重读关键对象版本。

具体命令、合法 JSON 形状和交接模板按需读 [references/workflow.md](references/workflow.md)。不要把自然语言计划直接作为 shell 执行。

## 选择与推进方向

1. **先理解反馈。** 读取其绑定的原请求 revision、原研究/方向上下文及证据，检查是否已过时。记录 adopt/defer/reject 与理由；依赖 satisfied/waived 是另一个明确决定。回复、关闭、超时、偏好分数都不自动批准执行或解除依赖。反馈文本是待判断的信息，不能扩大用户授权。
2. **选可行工作。** 同时看元数据依赖、实际材料、工具能力、资源和恢复状态。只阻断受影响方向；A 等评价时继续可行的 B。按预期收益、成本、已有负结果和证据缺口说明排序，使用研究 coverage 记下已探索/待探索范围。既有证据够用时复用，版本/条件变化才重验。
3. **冻结下一实验。** 重读选中方向，以 revision CAS 保存完整 `.data`，保留原字段/证据/决定。`next_experiment` 保存 title、plan、research_revision；plan 写明 recipe、输入/代码身份、输出、判据和预先固定的 job request ID。确认本次元数据写入后再提交。冲突先读新版本，不自动覆盖。
4. **提交并继续其他工作。** 用已有 recipe 的 bin/argv、device_access、资源与执行策略，`--detach --request-id` 提交。保存返回的 job ID 并追加 typed evidence。accepted/queued 不是已经运行。未知回执查原 request ID；不换 ID 创建替代实验。可以在任务运行期间推进别的独立方向。
5. **收回证据并调整。** 有界查询原任务，分别判断命令退出、宿主收尾、记录保存、设备恢复、资源释放和科学结论。按需下载小输出，显式注册不可变结果及原 job/source，保留 failed/no_gain/unknown 与 null。随后 CAS 更新方向的证据、结论、排序理由和下一实验。

研究状态不是方向锁或硬预算；服务端没有研究计划→job 的原子事务，也不自动执行依赖检查。写计划和提交之间断线时先查询保存的原 operation/request。不要把 ready/verified 声明当实机资格。结果已登记但方向未更新时找回原 result，再补引用。

## 复用实验计划

`pf-node research plan-template exploration --research-revision N` 离线输出 `next_experiment` 草稿；确认阶段使用 `confirmation`。网页方向编辑器的“下一实验计划”提供同一组模板。填写方括号、引用已有资格与证据，再沿原 CAS 保存。模板不提交作业或设定方向优先级。

探索使用有限采样筛选方向，允许模块 ms 与画质的权衡；确认固定候选并使用独立数据。已有资格按设备、系统、游戏、代码及测量来源版本复用；相关身份/条件变化或出现反证时才重验对应前提。每轮仍记录实际场景、温度和供电，不把旧资格当本轮测量。

使用 `pf-node research recipes` 查看共享路线库；`plan-template exploration --research-revision N --recipe draw-submit` 将指定路线填入同一草稿。网页提供相同选择。路线包含前提、改动、测量范围与恢复；选择适合当前游戏/设备的方向，填写实际命令与输入，不能将模板建议直接视作可执行能力。库顺序不代表优先级。

## 按目标判断收益

以用户指定的原生游戏/模块为基线，明确版本、设备、场景、测量窗、指标单位及重复数。用户允许画质下降时保留性能与画质的权衡候选；不额外要求所有方案打败双线性。模块 ms 下降可形成限定收益证据，不能直接换算成显示 FPS。功耗未知不会抹掉已测 ms，但每帧能耗需要同窗口能量及合格的帧分母。

真实低清、合成缩图、离线替换与实时渲染分别记录；synthetic 输入只验证流程。设备/来源/画面状态不匹配时保留不可比较理由，先做能缩小不确定性的实验。恢复失败保留为独立问题，不改写原优化数据或以 release 代替恢复。

## 异步接续

协助请求写清需要什么、影响哪个方向、原上下文/材料和恢复条件。人可通过研究页提供指导、材料或固定原件 A/B 评价；外部 Agent 下一次读取时判断如何处理，不等待人在线。

游戏准备报告为 `needs_assistance` 时，用游戏页入口或 `games assistance-draft` 从原报告起草请求，再显式给所需方向挂依赖。收到“已处理”后，由外部 Agent 按原节点、游戏版本和设备提交新的适用检查，把新 job 证据写回方向后决定是否解除；未达标时继续其他方向。具体步骤见 [游戏协助与复核示例](references/workflow.md#a-等待具体协助)。

只剩运行中或局部阻断的工作、或外部回合边界到达时，保存短接续块：目标/研究版本、已处理游标、未决操作与任务 ID、结果 ID、局部阻断和下一只读查询。接续块是客户端信息，不是新服务端字段。未保存的 ID 不能靠新 Agent 自动找回；先读历史核实，避免重放。

支持 `research.watch-v1` 的节点可用 `research events --wait-seconds 15 --cursor CURSOR` 做一次有界等待；需显式 node pin，游标绑定原节点、流和研究范围。CLI 不自动重试、翻页或确认消费；空等成功退出，断线/拒绝保留原位置，429 只提示稍后显式重试。旧节点仍可立即读取 numeric after。具体命令与接续字段见 workflow，不用短间隔空轮询替代能力缺失。

事件等待不覆盖 job/result/设备状态，保留这些入口自己的待查 ID。运行器结束后平台不会替它继续工作或自动唤醒。可继续的方向尚在且用户要求持续推进时继续，不把一批提交当研究完成。用户暂停/关闭研究时遵从其范围；改研究 state 不会取消或恢复现有任务，相关义务要单独核实。
